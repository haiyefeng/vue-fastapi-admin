## Context

小程序改造的阶段一（后端接口就位）已完成 20 个提交、196 个测试通过。下一步是让小程序连上后端，为此需要一个不依赖开发者本机环境的可运行服务。

仓库里已有一套容器配置，但它成型于本次改造之前：

```
┌──────────── app 容器 (:7777→:80) ─────────────┐
│  nginx :80                                    │
│    /      → web/dist        Vue 静态文件       │
│    /api/  → 127.0.0.1:9999                    │
│                                               │
│  python run.py → uvicorn :9999 (reload=True)  │
│    启动时 init_data():                         │
│      ① aerich migrate + upgrade  ← 自动改库    │
│      ② init_superuser/menus/apis/roles        │
│      ③ init_pet_config                        │
└───────────────────┬───────────────────────────┘
                    │ DB_HOST=mysql
        ┌───────────▼────────────┐
        │  mysql:8.1             │
        └────────────────────────┘
```

**已核实的现状**（非推测）：

- `.dockerignore` 写的是 `venv`，实际目录是 `.venv`；Docker 的 ignore 不做前缀模糊匹配，因此 128MB 本机虚拟环境（含 macOS 二进制）进入构建上下文，上下文总计 2.6GB。
- `deploy/entrypoint.sh` 执行 `python run.py`，而 `run.py` 写死 `reload=True`。
- `docker-compose.yml` 明文写死 `DB_PASSWORD=password123`，且没有 `WX_APPID` / `WX_SECRET`。
- `app_data` 卷挂在 `/opt/vue-fastapi-admin/data`，但没有任何代码写该路径（日志实际写 `app/logs`，未持久化）。
- `migrations/models/` 磁盘上只剩 `0_init`、`5_add_user_openid`、`6_add_pet_tables`；本机库的 aerich 表却记录了 0~6 共 7 条——**1~4 号文件已丢失**。
- `0_init` 只建 15 张表，缺 `habit` / `goal` / `review` / `time_block`。
- `init_db()` 有一条兜底分支：`migrate()` 抛 `AttributeError` 时 `rmtree("migrations")` 并从当前模型重建。**已实测**：对空库启动时正是走这条路径，最终建出 22 张表、关键表无缺失。

也就是说，容器现在「能跑」，但依赖的是「空库就把迁移目录删掉重来」这个兜底，而非版本库里的迁移文件。该分支已两次把本机开发库弄成半途状态。

## Goals / Non-Goals

**Goals:**

- 后端服务能在本机以容器方式跑起来，且与开发者本机已有的 MySQL 完全隔离
- 镜像的构建输入收敛到运行所需内容
- 容器内以生产方式运行，消除 reload 与自动迁移叠加产生的重启循环
- schema 可从版本控制重建：任何机器上的干净 clone 都能建出一致的完整 schema
- 保留一套面向群晖 NAS 的编排，与本机编排互不干扰

**Non-Goals:**

- HTTPS、证书、域名备案。小程序正式版必需，但与「服务能在容器里跑起来」正交，单独立项
- 多副本部署下的迁移竞态。当前是单实例
- 审计日志中间件对小程序热路径的放大问题（需产品判断排除哪些路径）
- 生产级镜像瘦身（非 root 用户、多阶段裁剪 apt 依赖等）

## Decisions

### D1: 迁移体系收归版本控制，启动只应用不生成

`init_db()` 改为只做 `upgrade()`，移除 `command.migrate()` 与 `rmtree` 兜底。

**为什么不是「启动什么都不做、部署时显式执行」**：那是更严格的形态，但会让本机开发和容器都多一个必须记住的步骤，而收益（防止启动期改 schema）在单实例场景下有限。「只应用、不生成」已经消灭了真正的痛点——**启动期向被监听目录写文件**，这正是循环的成因。迁移文件既然入库并经过评审，启动时应用它们是可接受的。

**为什么不保留兜底**：兜底的本质是「找不到可用历史就按当前模型重建」。它让 schema 的来源在「评审过的迁移」和「此刻的模型代码」之间不确定，而这种不确定恰恰在容器化后会被放大——镜像里带不带迁移文件决定走哪条路。

**替代方案**：保留兜底但只在检测到空库时启用。仍然保留了两条路径，复杂度不降反升。

### D2: squash 出单一干净基线，而非补齐丢失的 1~4 号

丢失的 1~4 号迁移文件无法恢复（它们只存在于本机库的 aerich 记账里）。做法是删掉现有全部迁移文件，从当前模型生成一个完整的 `0_init` 作为新基线。

**为什么可行**：现有的三个环境（开发者本机、将来的容器、将来的 NAS）中，只有本机库有数据，且其 schema 已与当前模型一致（`aerich migrate` 报「无变更」）。因此重置只需重写记账，不需要任何 DDL。

**代价**：丢失变更历史的可追溯性。考虑到 1~4 号本就已丢失，实际损失有限。

### D3: 本机编排自带 MySQL，与宿主机实例隔离

新建的 `docker-compose.yml` 启动 app + mysql 两个容器，使用独立 named volume。

**为什么不连宿主机的 MySQL**：`host.docker.internal` 能让容器复用本机 `plan` 库里的真实数据，看起来方便。但容器启动时 `init_data()` 会对该库执行 upgrade 与各类 init——也就是让容器里的代码去动开发者赖以工作的数据库。本次改造中已经因为「启动流程自动改真实库」出过两次事故，不应再引入同类耦合。

**代价**：容器里是空数据，`admin/123456` 由 `init_superuser()` 重新创建；要在容器里看到真实数据需要另行导入。这是可接受的——容器此刻的用途是「给小程序一个能连的后端」，不是「继续本机开发」。

### D4: 两份编排文件，NAS 那份原样保留

```
docker-compose.yml       ← 新建，本机，named volume
docker-compose.nas.yml   ← 现有文件重命名，保留 /volume2/... 绑定挂载
```

**为什么不用 override 机制**：`docker-compose.override.yml` 适合「同一套基础 + 少量差异」。本机与 NAS 的差异在数据卷形态、端口、重启策略上都不同，用 override 表达反而要读两个文件才知道实际配置。两份独立文件各自可读。

### D5: 改 entrypoint 而非改 `run.py`

`run.py` 是本机开发入口，热重载是它存在的意义。容器的生产化通过 `deploy/entrypoint.sh` 直接调用 uvicorn 实现。

**替代方案**：给 `run.py` 加环境变量开关（`RELOAD=false`）。可行，但让本机入口承担了容器的职责，且多一个必须正确设置的变量。

### D6: 用一条测试守住「迁移能在 MySQL 上执行」

本次改造中出现过一个只在真实迁移路径才暴露的缺陷：模型字段 `description` 里的单引号被 aerich 转义成 `\'` 写进迁移文件，而迁移文件是 Python 源码，`\'` 在字符串字面量里被 Python 求值成裸单引号，MySQL 收到 `COMMENT '...'...'` 直接语法错误。测试用 `generate_schemas()` 建表，不经过这条路径，因此测试全绿也发现不了。

已有的 `test_no_model_description_contains_single_quote` 守住了这一具体形态：它扫描所有模型的 `description`，禁止出现单引号。这是针对**已知缺陷形态**的窄守卫，成本极低；对整条迁移路径的验证由 D7 承担。

### D7: 用一项 MySQL 支撑的测试同时守住迁移的两个属性

新增一项测试：建一次性数据库 → 应用版本库中的迁移文件 → 断言（a）全部语句执行成功、（b）应用后模型无待生成变更、（c）过程中 `migrations/` 未被写入。

**为什么必须用真实 MySQL**：迁移 SQL 是 MySQL 方言，而现有测试用 `generate_schemas()` 建表——那条路径**完全绕开迁移文件**。本次改造已因此漏过一个会让应用启动崩溃的缺陷（见 D6），当时「MySQL 上验证过」的结论也是错的，因为验的是 `generate_schemas()` 而非 `aerich upgrade`。**`generate_schemas()` 的绿色不构成对迁移路径的验证**，这一条要写进设计而不只是记在心里。

**为什么不放到启动时检测**：spec 早先的写法要求「启动时以可诊断方式暴露模型与迁移的不一致」，但 D1 定的 `init_db()` 只做 `upgrade()`，而 `upgrade()` 只应用磁盘上待应用的文件、根本不比对模型——需求要求检测，设计却没有提供机制。放到测试层解决了这个矛盾，而且提交时就能拦住，比启动时才发现早得多，也不给启动流程增加负担。

**隔离要求写死在 tasks 里**：该测试 MUST 在独立子进程中、靠环境变量指定库名。调查阶段有一次同类测试试图靠在进程内修改已导入的 settings 对象来切库，结果隔离失败，往开发者的工作库写进了一条幽灵记账。这个失败模式已知且必须避免。

**代价**：这是唯一需要外部服务的测试。MySQL 不可达时跳过并给出明确原因——跳过是可见的，静默通过不是。

## Risks / Trade-offs

- **[基线重置搞错顺序会让本机库与迁移记账错位]** → 重置只重写记账、不执行 DDL；执行前后各跑一次 `aerich migrate`，前者确认「无变更」（证明 schema 已一致）、后者同样确认「无变更」（证明记账已对齐）。任何一次不是「无变更」即中止。
- **[移除兜底后，模型改了但没生成迁移，启动不再报错]** → 这是有意的取舍：启动只应用、不判断（D1），一致性由 D7 的测试在提交前拦截。代价是若绕过测试直接部署，容器会带着旧 schema 正常启动、直到访问新字段才出错。接受该代价的前提是 D7 的测试真的会被执行——因此 tasks 要求它在 MySQL 不可达时**跳过并打印原因**，而不是静默通过。
- **[迁移文件整体缺失（如 `.dockerignore` 误排除）会让容器带着空库启动]** → `upgrade()` 无文件可应用时不会建任何表，应用照常启动、首次查询才失败。由 tasks 的端到端验证（检查容器内 22 张表）拦截。
- **[容器里是空数据，可能与「我想看到我的待办」的预期不符]** → 在 tasks 中明确说明，并保留 `docker-compose.nas.yml` 的绑定挂载形态供将来接真实数据。
- **[`.dockerignore` 排除过多导致构建缺文件]** → 排除项逐条对应「后端运行时不需要」，且通过一次真实构建 + 启动验证，而非仅靠推断。
- **[改 entrypoint 后 nginx 与 uvicorn 的启动顺序/存活关系变化]** → 现状是 `nginx` 后台启动、`python run.py` 前台阻塞；改动保持同样形态（nginx 后台 + uvicorn 前台），不引入进程管理器。
- **[迁移一致性测试依赖外部 MySQL，可能在缺少该服务的环境里长期处于跳过状态]** → 跳过时必须打印原因；若将来接入 CI，该服务是必备依赖而非可选项。
- **[首次启动仍可能出现一次重启]** → 移除自动 migrate 后启动期不再写文件，该重启的成因消失；以「首次启动无多余重启」作为验收条件之一。

## Migration Plan

1. **准备**：确认 dev server 已停止（本次改造中该进程与自动迁移叠加已两次造成事故）
2. **重建基线**：删除现有迁移文件 → 从当前模型生成完整的 `0_init` → 确认其 SQL 能在临时数据库上真实执行
3. **重置本机库记账**：清空 aerich 表并写入指向新基线的单条记录；前后各验证一次「无变更」
4. **改代码**：`init_db()` 移除 migrate 与 rmtree
5. **改配置**：`.dockerignore`、`entrypoint.sh`、`.env.example`、`.gitignore`
6. **拆编排**：现有 `docker-compose.yml` → `docker-compose.nas.yml`；新建本机版
7. **验证**：`docker compose up --build` 实跑，验证首次启动无多余重启、schema 完整、接口可访问
8. **回滚**：本次改动集中在配置与启动流程，回滚即 `git revert`；本机库的记账重置需手工还原（重置前先导出 aerich 表内容备查）

## Open Questions

- ~~日志卷的挂载点~~ **已在写实施计划时查明并推翻**：本应用根本不写日志文件。`app/log/log.py` 里只有 `add(sink=sys.stdout)` 一个 sink，文件 sink 那行是注释掉的；`settings.LOGS_ROOT` 定义了但全仓无人引用，`app/logs/` 目录都不存在。原先「把 `app_data` 卷改挂到 `app/logs`」的方案，等于把同一个错误换个挂载点再犯一遍。结论：**编排里不声明任何日志卷**，日志作为事件流输出到 stdout 交由容器运行时收集（这本就是容器的标准做法）。若将来确需落盘日志，那是一项独立改动：启用文件 sink + 挂卷。
- 容器内是否需要预置微信凭据才算「启动成功」：当前设计是缺失时告警而非阻止启动，因为后端的其余功能不依赖它。
